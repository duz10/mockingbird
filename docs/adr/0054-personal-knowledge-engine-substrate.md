# ADR-0054: Personal Knowledge Engine substrate (Karpathy/Clark adoption)

- **Status:** Proposed
- **Date:** 2026-06-06
- **Deciders:** Dustin (project lead), Bernard (code-puppy, implementor)
- **Charters:** `mb-rik9` (Phase 1E Alignment Wave)
- **Adopts richer framing of:** ADR 0049 (KG architectural pivot),
  ADR 0053 (KG Phase 1E — Obsidian as source of truth)
- **Partially supersedes:** ADR 0053 §D3 (type vocabulary), §D8
  (Wave 1E.7 seeds scope), §D9 (Tasks-plugin checkbox default-on)

---

## Context

The KG epic was originally framed via ADR 0049 (architectural pivot to
schema-driven pipeline + opt-in graph) and ADR 0053 (Phase 1E: Obsidian
as the source of truth via two-phase commit + reverse-watcher). Both
ADRs are correct as far as they go. The capture pipeline ships content
into the vault; the vault is canonical; reverse-edits reconcile back.

Two foundational references surfaced after ADR 0053 sealed that clarify
the bigger picture neither prior ADR named:

- **Andrej Karpathy's "LLM Wiki" gist** (the canonical
  compile-once-query-many insight). The LLM is treated as a *compiler*
  for sources, not a search engine over them. Raw sources are
  compiled once into a structured, interlinked wiki; future queries
  run against pre-synthesized knowledge.
- **Alvin Clark's "Building a Personal Knowledge Engine with LLMs and
  Obsidian"** (April 2026). Concretizes Karpathy's pattern over an
  Obsidian vault: three-layer architecture (raw immutable / wiki
  LLM-maintained / operational contract), three operations (Ingest /
  Query / Lint), and a small load-bearing set of vault-resident
  artifacts (`SCHEMA.md`, `INDEX.md`, `LOG.md`).

Re-reading our work through this lens exposes a clarifying insight that
neither ADR 0049 nor ADR 0053 captured cleanly:

> **There are two agents in this system, not one. Mockingbird is the
> capture + first-pass synthesis layer; the user's chat-LLM (Claude
> Code / Cursor / OpenCode / etc.) is the wiki author/maintainer.**

This ADR does NOT supersede ADR 0053 wholesale. ADR 0053's substrate
(`Entries/` + `Entities/` + `Projects/` + History/Inbox + two-phase
commit + reverse-watcher) is the *foundation*. This ADR ADOPTS a
richer architectural framing that ADR 0053's substrate fits within,
and rescopes the remaining Phase 1E waves (1E.7/1E.8/1E.9) plus the
downstream Phase 2 charter to align with it.

The architectural lineage runs back to Vannevar Bush's Memex (1945) —
personal, curated, associative trails between documents. As Karpathy
puts it: *"The part [Bush] couldn't solve was who does the
maintenance. The LLM handles that."*

---

## Decision

We adopt the Karpathy/Clark Personal Knowledge Engine pattern as
Mockingbird's KG architectural north star.

Concretely:

1. Define a **three-layer architecture** for the vault (raw immutable /
   wiki LLM-maintained / operational contract).
2. Define a **two-agent role separation** between Mockingbird (capture +
   first-pass synthesis) and the user's chat-LLM (wiki author).
3. Add three new vault-resident artifacts as load-bearing: `SCHEMA.md`
   (write-once user-owned), `INDEX.md` (auto-maintained catalog),
   `LOG.md` (append-only operations record).
4. Add a `Tags/` subtree parallel to `Entities/` and `Projects/` —
   auto-generated tag pages with Dataview rollups, same write-once
   user-owns-thereafter contract as entity/project pages.
5. **Realign type vocabulary to knowledge shapes** (`source` / `note` /
   `concept` / `entity` / `project` / `question` / `decision` /
   `reference` / `observation`). Drop `task` and `event` from the
   canonical vocabulary. Resolves the ADR 0053 §D3 vs `kg::schema`
   vocab drift (`mb-il83`) by redefining the canonical set.
6. **Drop task-management surfaces.** No Kanban board seed in Wave
   1E.7. The Obsidian Tasks plugin remains a passive ecosystem fit
   (users who want checkboxes can write them), but Mockingbird does
   NOT default-on Tasks-plugin checkboxes on every entry, does NOT
   build a Kanban view, and does NOT seed Kanban view templates.
7. Define Phase 2 scope as **Mockingbird-side enrichments only**,
   not "all six operations." Most of what was originally bucketed as
   "Phase 2: Personal Knowledge Engine" lives in the chat-LLM, not in
   Mockingbird.

The eight binding principles in `.code_puppy/AGENTS.md` are
unaffected; this ADR is a framing + scoping decision over the same
substrate.

## §A. Three-layer architecture

```
Layer 3 — SCHEMA.md (operational contract; vault-resident)
   │
   ▼
Layer 2 — Wiki (LLM-maintained; ripple-on-source-change)
   • Entries/          source notes from capture
   • Entities/         per-entity pages (Mockingbird stubs; chat-LLM enriches)
   • Projects/         per-project pages (Mockingbird stubs; chat-LLM enriches)
   • Tags/             per-tag pages (auto-generated by Mockingbird; Dataview rollups)
   • Source summaries  authored by the chat-LLM as it ingests new sources
   • Concept pages     authored by the chat-LLM as new concepts emerge
   • Runbooks          authored by the chat-LLM as multi-step procedures crystallize
   │
   ▼
Layer 1 — Raw sources (content-immutable; LLM reads, never modifies)
   • History/<YYYY-MM>/<session-uuid>.{json,wav,mp3,...}
   • Inbox/<source>/<file>
```

**Layer 1** is the capture record. Mockingbird writes it; nobody
modifies it. This matches Principle 1 ("raw data is immutable") from
`AGENTS.md`.

**Layer 2** is the wiki. Mockingbird writes the *first-pass* shape of
it (clean Entries with frontmatter + body, stub Entity/Project/Tag
pages with Dataview rollups, INDEX.md catalog, LOG.md operations log).
The user's chat-LLM is responsible for the *deep* shape — source
summaries, concept extraction beyond per-segment, runbook authoring,
ripple updates across pages when a source changes a downstream
concept, contradiction resolution, etc.

**Layer 3** is `SCHEMA.md` — the operational contract any LLM reads to
maintain the wiki consistently. Preferences travel with the file, not
the model. This is the load-bearing artifact that makes the wiki
*portable across chat-LLM products*. If the user moves from Claude
Code to Cursor next week, the new chat-LLM reads `SCHEMA.md` and is
immediately calibrated.

## §B. Two-agent role separation

```
┌────────────────────────────────────────────────┐
│ User's chat-LLM (Claude Code / Cursor / etc.)  │
│ • Reads SCHEMA.md                              │
│ • Performs INGEST / QUERY / LINT               │
│ • Ripple updates across 10-15 wiki pages       │
│ • Files good answers back as new wiki pages    │
└──────┬─────────────────────────────────────┬───┘
       │ reads/writes                        │
       ▼                                     │
┌────────────────────────┐                   │
│ Obsidian Vault         │                   │
│ Knowledge Graph/       │                   │
│  ├── SCHEMA.md         │ ◄─────────────────┘
│  ├── INDEX.md          │
│  ├── LOG.md            │
│  ├── Entries/          │ ◄──────────┐
│  ├── Entities/         │            │
│  ├── Projects/         │            │
│  ├── Tags/             │            │
│  ├── Inbox/  (Layer 1) │ ◄──────────┤ writes
│  └── History/(Layer 1) │            │
└────────────────────────┘            │
                                      │
┌─────────────────────────────────────┴───┐
│ Mockingbird (desktop + mobile)          │
│ • Audio + text capture (zero friction)  │
│ • First-pass synthesis (clean/class/    │
│   extract entities / wiki-link emit)    │
│ • Maintains INDEX.md + LOG.md           │
│ • Reverse-watcher (file-wins)           │
└─────────────────────────────────────────┘
```

### Mockingbird's responsibilities

- Zero-friction capture (PTT dictation; KG-note dictation; text notes;
  mobile audio via KG-Inbox courier; iOS Shortcut intake)
- First-pass synthesis per segment: cleanup → classify → extract
  entities → tag → wiki-link emission
- Deterministic Markdown projection to `Entries/`
- Auto-generated stub pages for `Entities/`, `Projects/`, `Tags/`
  (write-once; user-owns-thereafter)
- `INDEX.md` catalog maintenance (additive on each new Entry; never
  rewrites user edits)
- `LOG.md` append-only operations log
- Reverse-watcher (Obsidian edits to `Entries/` reconcile back into
  SQLite, file-wins)
- History archive (Layer 1 sidecars per session)

### Chat-LLM's responsibilities

- Read `SCHEMA.md` at session start
- **Ingest** — when the user drops a new source (article, photo,
  transcript, link), integrate it across the wiki. Update the relevant
  source-summary page; ripple updates to concept pages, entity pages,
  project pages. A single ingest can touch 10-15 pages.
- **Query** — answer questions against the wiki using its search/drill
  tools. File good query results back as new wiki pages so future
  explorations compound (this is the "knowledge compounds" behaviour
  Karpathy calls out).
- **Lint** — periodic health check. Surface contradictions between
  pages, stale claims (sources updated but downstream pages didn't
  ripple), orphan entities (mentioned but no page), missing concepts
  (used informally across pages but no canonical definition).
- Append to `LOG.md` after each significant operation.

### Where does Mockingbird stop?

Mockingbird's `kg::extract_entities` pass extracts entities + tags from
*the current segment in isolation*. It does NOT:

- Reconcile a new entity mention against existing entity pages
  (the chat-LLM does this on Ingest)
- Update the body of an existing concept page when a new source
  contradicts it (the chat-LLM does this on Ingest)
- Synthesize cross-source patterns into new concept pages (the
  chat-LLM does this on Query / Lint)
- Detect orphan entities or stale claims (the chat-LLM does this on
  Lint)

This is the *first-pass* in "first-pass synthesis" — shallow, fast,
local, deterministic. The deep pass is the chat-LLM's job and runs
when the user invokes it, not on every capture.

## §C. SCHEMA.md

**Status:** write-once user-owned (Mockingbird seeds it on first
activation if absent; never rewrites thereafter).

**Purpose:** operational contract for any LLM (chat-LLM or otherwise)
that maintains the wiki. Preferences travel with the file.

**Contents (suggested seed — user edits freely):**

- **Folder structure:** which folders Mockingbird auto-maintains
  (`Entries/`, `Entities/`, `Projects/`, `Tags/`, `History/`,
  `Inbox/`) and which are user-owned (everything else under
  `Knowledge Graph/`)
- **Page templates:** frontmatter shape per page type, body conventions
  (Dataview blocks, callout usage, link styles)
- **Wiki-link conventions:** entity slugs are kebab-case ASCII;
  entities emit as `[[Entities/<slug>|<slug>]]`; project pages get
  `[[Projects/<slug>]]`; tag pages get `[[Tags/<slug>]]`
- **Type vocabulary:** the nine knowledge shapes (see §G)
- **Workflows:** how to perform Ingest / Query / Lint over this vault
- **Accumulated user preferences:** "I prefer concise summaries"; "I
  use 'project' for anything multi-session not just professional";
  "I prefer en-US spelling"; etc. The chat-LLM adds to this section
  over time as preferences crystallize.

**Format:** Markdown with YAML frontmatter `schema_version: 1`.

**Mockingbird's interaction:** read-only (Mockingbird does NOT consume
SCHEMA.md for its capture pipeline — its pipeline is pre-calibrated by
the v1 prompts. SCHEMA.md is for the *other agent*, the chat-LLM).
Mockingbird seeds it on first activation if missing.

## §D. INDEX.md

**Status:** auto-maintained by the Mockingbird worker. Additive on
each new Entry/Entity/Project/Tag page. User edits to non-managed
sections are preserved.

**Purpose:** content catalog so the chat-LLM can answer "what do we
have on X?" without re-walking the filesystem on every query.

**Format:** Markdown with H2 sections per category:

```markdown
## Sources         (links to Entries/<recent>; capped at most-recent N)
## Entities        (links to Entities/<all>; alphabetical)
## Projects        (links to Projects/<all>; alphabetical)
## Tags            (links to Tags/<all>; alphabetical)
## Concepts        (chat-LLM-authored concept pages; alphabetical)
```

**Mockingbird's writes:** updates the Sources / Entities / Projects /
Tags sections when their corresponding pages are created. Never
touches the Concepts section (chat-LLM-owned).

**Update cadence:** on each successful KG worker `process_one` that
either creates a new Entry or ensures a new stub page. Not a periodic
rebuild — incremental.

---

## §E. LOG.md

**Status:** append-only operations record. Both Mockingbird worker
and chat-LLM append to it.

**Purpose:** chronological narrative of what happened to the vault.
The chat-LLM reads it on session start to catch up on what Mockingbird
captured since last session. Useful for Lint operations (recent
captures often surface new concepts that need formal pages).

**Format:**

```markdown
## [2026-06-06 14:32] capture | "Mockingbird is going well..."
## [2026-06-06 14:35] ingest | source: Karpathy LLM Wiki gist
## [2026-06-06 15:01] lint | found 3 orphan entities: maple, jensen, costco
## [2026-06-06 15:08] query | "what's outstanding on the KG epic?"
```

Format spec:

- `## [YYYY-MM-DD HH:MM] operation | title` — header line per entry
- Optional body indented underneath for context (Mockingbird leaves
  body empty; chat-LLM may add 1-2 lines of context)
- One blank line between entries
- LF line endings (LESSONS P12 Finding 1 — file-write tools default
  to CRLF on Windows; the writer must normalize)

**Mockingbird's writes:** appends a `capture` line on each successful
Entry projection (post-vault-seal). Never reads or rewrites prior
entries. Failure to append is logged + swallowed (the LOG.md is a
convenience, not a correctness invariant).

**Append discipline:** read-tail-then-append, with O_APPEND on the
file handle. No `read-modify-write` rewrites — many other processes
(chat-LLM, Obsidian Sync) may also append concurrently.

## §F. Tags/ subtree

**Status:** parallel to `Entities/` and `Projects/`. Auto-generated
stub pages per tag; write-once; user-owns-thereafter. Same pattern as
§D11 (Entity pages) and §D12 (Project pages) from ADR 0053
amendments.

**Subtree layout:**

```
Knowledge Graph/
├── Tags/
│   ├── grocery.md
│   ├── side-project.md
│   ├── work.md
│   └── ...
```

**Filename:** `<slug>.md` where `<slug>` is the kebab-case ASCII form
of the tag.

**Page template (stub):**

```markdown
---
type: tag
slug: <slug>
created: <ISO-8601 UTC>
schema_version: 1
---

# <slug>

```dataview
table type, status, captured
from "Knowledge Graph/Entries"
where contains(tags, "<slug>")
sort captured desc
```
```

**Generation:** Mockingbird worker after each `process_one` that
produced segment-level tags collects unique tag slugs from
`result.segment_tags`, calls `ensure_tag_page(slug)` for each. Stub
creation is non-fatal; logged + swallowed on failure.

**Wiki-link emission:** Entries' frontmatter `tags:` field continues
to emit bare slugs (matches the Obsidian tag ecosystem `#slug`
convention). The Tags/ pages let the user click an entry's tag chip
in Obsidian and land on a page listing all entries with that tag —
which without the page would 404. Tag pages also enable typed
backlinks (the Obsidian graph view treats `[[Tags/<slug>]]` mentions
in body as edges).

**Implementation lives in:** Wave 1E.7 (re-scoped per this ADR §J).

## §G. Type vocabulary realignment

**Drop:** `task`, `event` (task-management-flavored; off-axis with the
knowledge-engine pattern).

**New canonical vocabulary — nine knowledge shapes:**

| Shape | Meaning |
|---|---|
| `source` | An Entry whose primary value is the raw material itself — a transcript, an article reference, a memo. Default for every `Entries/` file unless another shape applies. |
| `note` | A short observation or aside that doesn't rise to source-level. Quick thought, brief reaction. |
| `concept` | A definition or explanation of an idea. Tends to migrate to a dedicated concept page in `Entries/Concepts/` (chat-LLM-authored). |
| `entity` | A reference-to-an-entity entry. The body is *about* the entity; the page in `Entities/<slug>.md` is the durable home. |
| `project` | A reference-to-a-project entry. Body is *about* the project; the page in `Projects/<slug>.md` is the durable home. |
| `question` | An open question. Useful for Lint (surface unanswered questions). |
| `decision` | A point-in-time decision record. Body should capture context + decision + consequences (ADR-like, but lightweight). |
| `reference` | A pointer to external material the user wants to preserve a handle to (URL, book chapter, conversation). |
| `observation` | A noticing — pattern, anomaly, surprise. Useful raw material for chat-LLM Lint to crystallize into concepts. |

**Note on "every Entry is implicitly a source":** the YAML
frontmatter `type:` field describes the *knowledge shape* of the
entry. Even a `decision`-typed Entry is also implicitly a source (the
raw material is the decision-recording dictation). Source-summary
pages authored by the chat-LLM go in a separate `Entries/Summaries/`
or `Sources/` subtree and reference the original `Entries/` file via
wiki-link.

**Migration path:**

- **Existing entries:** leave as-is. Backfill is cheaper to defer
  than to design (LESSONS P14 Finding 3 from the 2026-06-06 mb-08za
  iteration). Dataview queries can defensively `OR` legacy and new
  vocabulary if needed.
- **New entries:** classifier prompt + few-shot examples updated to
  the new vocabulary as part of `mb-xqcf` (re-scoped per §J below).
- **Serializer:** `vault::markdown_serializer::EntryType` enum
  expanded to the nine knowledge shapes. The drift bead `mb-il83` is
  closed by this realignment — the vault serializer and `kg::schema`
  now align on the new canonical set, and the lossy `Research/Reference
  → Note` mapping at the worker boundary is replaced by the new
  vocab pass-through.

**`kg::schema::EntryType` reconciliation:** the v1 enum
`Task/Research/Idea/Note/Reference` becomes the v2 enum
`Source/Note/Concept/Entity/Project/Question/Decision/Reference/Observation`.
`Task` and `Idea` are dropped (Idea → `note` or `observation`
depending on shape; Task → `note` in v1 backfill; Research → `concept`
or `reference` depending on shape; Note → `note`; Reference →
`reference`). Done at Phase 2 implementation time; this ADR
charters the vocabulary, not the migration code.

## §H. Operations that belong to the chat-LLM

These are NOT Mockingbird-side features. The chat-LLM (Claude Code,
Cursor, OpenCode, etc.) performs these reading from the vault and
SCHEMA.md.

### Ingest

User drops a new source into the chat-LLM's working context (paste a
link, drop an article, reference a `Entries/<date>-<slug>.md` file).
The chat-LLM:

1. Reads SCHEMA.md for conventions
2. Reads relevant existing pages (entities mentioned in the source,
   adjacent concepts, the project page if applicable)
3. Synthesizes a source-summary page (or updates an existing one)
4. Ripples updates: refreshes the entity pages with new mentions,
   updates the project page's "Recent activity", adds new concepts if
   the source introduces them, contradicts and resolves stale claims
5. Appends a `## [...] ingest | <source title>` line to LOG.md

A single Ingest can touch 10-15 pages. This is the high-leverage
operation in the Karpathy pattern.

### Query

User asks a question in the chat-LLM. The chat-LLM:

1. Uses its search/grep tool to find relevant pages (frontmatter
   queries, full-text search, tag rollups via Dataview)
2. Drills into the relevant pages
3. Synthesizes an answer with inline citations linking back to
   `[[Entries/<file>]]` / `[[Concepts/<file>]]` / etc.
4. If the answer is general-purpose (not query-specific), files it
   back as a new concept page or appendix to an existing concept page
   so the next session compounds on it
5. Appends a `## [...] query | <question>` line to LOG.md

### Lint

Periodic health check, user-invoked or chat-LLM-self-scheduled. The
chat-LLM:

1. Walks the vault collecting structural facts (entities mentioned but
   no page; pages with no inbound links; stale claims where the source
   has been updated but the downstream page hasn't rippled;
   contradictions between pages)
2. Surfaces a punch-list in chat for the user to triage
3. With user approval, runs fix operations (create missing entity
   pages with stub content; ripple stale claims; merge duplicate
   entities)
4. Appends a `## [...] lint | <summary>` line to LOG.md

**Mockingbird-side surfacing (optional, Phase 2):** Mockingbird could
expose a "Lint hints" surface on the KG screen listing orphan
entities / missing tags / stale entries, with a "Open in chat-LLM"
deep-link that pastes a starter prompt. Mockingbird *surfaces*; the
chat-LLM *fixes*. See §K.

## §I. Operations that stay in Mockingbird

These ARE Mockingbird's job and stay on its side of the line.

- **Capture** — audio + text intake; PTT dictation; KG-note dictation;
  text notes; KG-Inbox courier; iOS Shortcut intake.
- **First-pass synthesis** — segment → classify → extract entities →
  tag → wiki-link emit. Per-segment, in isolation, no cross-vault
  reasoning. Calibrated for ~1 min intake latency budget (ADR 0049).
- **Deterministic Markdown projection** — `vault::markdown_serializer`
  emits canonical-LF Entries to `Knowledge Graph/Entries/`.
- **Auto-generated stub pages** — Entities/, Projects/, Tags/. Each
  per ADR 0053 §D11 + §D12 + this ADR §F. Write-once; user-owns-
  thereafter.
- **INDEX.md maintenance** — additive, on each new page.
- **LOG.md append** — one line per `capture` operation.
- **Reverse-watcher** — Obsidian edits to `Entries/` files reconcile
  back into SQLite (file-wins, hash-based loop-prevention).
- **History archive** — Layer 1 raw-immutable sidecars per session
  (per ADR 0053 §D7).
- **Optional Phase 2 enrichments** — concept extraction in the
  pipeline; source-summary distinction; lint-hint surfacing;
  chat-LLM convenience launcher. See §K.

**Notably NOT Mockingbird's job:**

- Ingest-ripple across pages (chat-LLM)
- Query engine (chat-LLM uses its native tools)
- Lint engine (chat-LLM)
- Concept page authoring beyond per-segment extraction (chat-LLM)
- Source-summary authoring (chat-LLM)
- Runbook authoring (chat-LLM)

## §J. Phase 1E wave re-scoping

This section concretizes the rescope of the remaining Phase 1E waves
(those not yet sealed at this ADR's authoring time).

### Wave 1E.6 — KG-Inbox courier — UNCHANGED

Sibling to ADR 0046 inbox; positional routing per ADR 0048 Q2; shared
dedup ledger. The KG-Inbox is the mobile capture intake; its scope is
orthogonal to the Karpathy/Clark adoption and ships as charted.

### Wave 1E.7 — Re-scoped: SCHEMA.md / INDEX.md / LOG.md / Tags subtree

**Drops:**

- `Kanban-Tasks.md` seed (was D8.iii in ADR 0053 §D8). The Kanban
  view contract was task-management-flavored and is off-axis with
  the knowledge-engine pivot. No Kanban seed; users who want a
  Kanban over their Entries can install the Kanban plugin
  themselves and configure it.
- `Dashboard.md` seed in its task-flavored shape (was D8.i in ADR
  0053 §D8). A simpler `INDEX.md` (per §D of this ADR) replaces it.

**Adds:**

- **`SCHEMA.md` seed** — write-once user-owned; only seeded if
  missing. Content per §C above.
- **`INDEX.md` seed** — auto-maintained catalog; seeded with the H2
  scaffold; populated incrementally as new pages land. Content per
  §D above.
- **`LOG.md` seed** — append-only operations log; seeded with a
  header line documenting the format. Content per §E above.
- **`Tags/` subtree** — created as part of `bootstrap_kg_subtree`
  (parallel to existing `Entities/`, `Projects/`, `History/`,
  `Inbox/`, `Entries/`). Per-tag stub pages auto-generated by the
  worker, per §F above.
- **Type vocabulary realignment** in the serializer and goldens —
  `vault::markdown_serializer::EntryType` enum expanded to the nine
  knowledge shapes; lossy `Research/Reference → Note` mapping at the
  worker boundary replaced by direct pass-through; goldens updated.
- **README.md seed** — short orientation pointing the user at
  SCHEMA.md, the chat-LLM workflow, the Karpathy/Clark pattern, and
  the open-format guarantee.

### Wave 1E.8 — iOS Shortcut docs — framing updated

The iOS Shortcut docs shape (`docs/mobile/ios-shortcut-kg.md`) is
unchanged from ADR 0053 §D10. Framing in the doc body shifts: the
Shortcut delivers content to `Inbox/` (Layer 1 raw); the chat-LLM
Ingest operation crystallizes it into Layer 2 wiki pages later.
Mockingbird-side: KG-Inbox courier's job is the same (drop file →
classify → enqueue for first-pass synthesis).

### Wave 1E.9 — Judges + seal — framing updated

The four judges (J1–J4) carry over from ADR 0053:

- J1 `kg-reverse-watcher-loop-prevention` — UNCHANGED
- J2 `kg-file-wins-on-conflict` — UNCHANGED
- J3 `kg-subtree-bootstrap-idempotent` — extended to cover the new
  artifacts (SCHEMA.md / INDEX.md / LOG.md / Tags subtree); the
  five-folder + three-file shape must be idempotent under
  back-to-back bootstraps.
- J4 `kg-serializer-golden-roundtrip` — extended goldens cover the
  new type vocabulary.

The semantic shift in judges is from "task semantics" (was: Kanban
seeded, Tasks-plugin checkboxes round-trip on the default-on path) to
"knowledge-link semantics" (auto-generated stub pages exist for every
entity/project/tag mention; wiki-link emission is byte-stable; the
INDEX.md catalog covers what was created).

## §K. Phase 2 scope clarification

Originally framed as a multi-wave "Personal Knowledge Engine" epic.
With the chat-LLM doing the heavy lifting (Ingest / Query / Lint),
Phase 2 for Mockingbird shrinks substantially.

**Mockingbird-side enrichments only:**

1. **Concept extraction** — extend the pipeline with an optional
   `extract_concepts` pass that surfaces concept-shaped extractions
   distinct from entity-shaped ones. Pure first-pass; the chat-LLM
   does the durable concept-page authoring.
2. **Source-summary distinction** — first-pass-emit a one-paragraph
   `summary:` field in Entry frontmatter (already present in the
   ADR 0053 schema) populated from the cleanup pass, not just
   defaulted to `null`. The chat-LLM's source-summary pages live in
   a different subtree; Mockingbird's `summary:` is the *call-out*
   surface for INDEX.md.
3. **Lint-hint surfacing (optional)** — KG dashboard "Lint hints"
   band listing orphan entities (mentioned in Entries but no page),
   missing tags (slugs used but no Tags/ page), and stale entries
   (last-modified > N days, status not closed). Mockingbird only
   surfaces; the chat-LLM fixes via Ingest/Lint.
4. **"Open in chat-LLM with vault context" launcher (optional)** —
   one-click button on the KG screen that opens the user's
   configured chat-LLM (Claude Code, Cursor, etc.) with a pasted
   starter prompt: "Read SCHEMA.md at <vault>/SCHEMA.md; perform
   Lint over <vault>/." Convenience; not load-bearing.
5. **INDEX.md / LOG.md incremental-maintenance refinements** —
   batched writes; conflict-tolerant append; recovery from torn
   writes; section-level diff-aware updates.

**Likely 1 phase**, not multi-wave. Detailed scope/sequencing in a
future ADR (provisionally 0055).

## §N. Consequences

### Positive

- The architectural north star is now named. Future sessions resume
  on "Karpathy/Clark Personal Knowledge Engine substrate" without
  having to re-derive the framing.
- Two-agent role separation gives both Mockingbird and the chat-LLM
  scoped jobs. No more "should Mockingbird do this or is that the
  chat-LLM's job" ambiguity.
- SCHEMA.md as portable contract means the vault outlives any
  specific chat-LLM product choice.
- Type vocabulary realignment closes `mb-il83` cleanly (the drift
  was symptom; vocabulary mis-design was cause).
- Phase 2 scope shrinks from multi-wave epic to probably-one-phase.

### Negative

- Existing entries written with the old vocabulary stay legacy. New
  entries get the new vocabulary. Dataview queries that span the
  boundary need defensive `OR`s. Acceptable per the
  "backfill-is-cheaper-to-defer" precedent (LESSONS 2026-06-06
  mb-08za Finding 3).
- The Kanban-Tasks.md seed work that was planned for 1E.7 is dropped.
  Users who want a Kanban over Entries install the Kanban plugin
  themselves. Net: less out-of-box polish on the
  task-management-flavored surface, more conceptual coherence.
- Documentation realignment cost: STATUS.md, PRODUCT-STATE.md,
  AGENTS.md, LESSONS.md, ADR 0053 pointer, phase-1e.md, spec.md
  (deferred via P2 bead). Paid in this Alignment Wave; no future
  carry.

### Neutral

- `kg::schema::EntryType` enum + `vault::markdown_serializer::EntryType`
  enum still need to be reconciled in code, just to a different
  target. Work moves from `mb-il83` (closed) to Wave 1E.7's
  type-vocab-realignment scope.
- The Obsidian Tasks plugin remains a passive ecosystem fit. Users
  can opt into Tasks-checkbox emission via a setting. The shape
  doesn't go away; it just stops being the *default*.

## §O. Open questions (for Phase 2 charter)

These are deliberately left open here; the Phase 2 charter ADR
(provisionally 0055) resolves them with concrete decisions.

1. **Concept-extraction pass placement** — is it a 6th pipeline pass
   parallel to entity extraction, or a post-processor over the
   normalized output? Empirical question; needs a Phase 0.5-style
   probe at Phase 2 kickoff.
2. **Source-summary `summary:` field generation** — populated from
   the cleanup pass output (existing LLM call), or a separate
   summarize-pass? Latency trade-off; needs a measurement.
3. **Lint-hint surfacing latency** — periodic background scan, or
   on-demand button-click, or both? Affects database schema (do we
   need a `kg_lint_hints` materialized table?).
4. **"Open in chat-LLM" launcher protocol** — how does Mockingbird
   detect which chat-LLM the user has configured (Claude Code,
   Cursor, OpenCode, generic-Claude.ai, generic-ChatGPT.com)?
   Settings dropdown + URL templates is the obvious answer;
   confirm at charter time.
5. **INDEX.md torn-write recovery** — under what conditions can
   Mockingbird's incremental update collide with a concurrent
   chat-LLM-driven rewrite, and what's the recovery? Options:
   read-tail-verify-append (append-only sections only); fsync +
   rename atomic swap (full-rewrite sections); leave it lossy and
   surface a "regenerate INDEX.md" button. Likely option 1 + 3.
6. **Vocabulary backfill window** — when (if ever) do we offer a
   one-click "remap legacy entries to new vocabulary" action?
   Probably never; defer indefinitely unless user-asked.
